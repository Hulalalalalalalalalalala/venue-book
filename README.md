# roottrace

roottrace 计算数据批次的 Merkle 根值，用于比较两个批次的内容是否一致。

## 构建

```sh
cargo build --offline
```

## 测试

```sh
cargo test --offline
```

除单元测试（SHA-256 向量、记录划分、MTH 递归构造、包含证明逐位置验证）外，
`tests/root_regression.rs` 通过实际构建出的命令做端到端回归：以事先固定的完整
根值校验 7、8、9 条记录（跨过 8 条这一二次幂边界）三个共享前七条记录的固定批次，
并覆盖重复内容改一个位置、交换两条不同记录、遗漏空记录、重复纳入一条记录、
末尾 LF 有无等价，以及空文件与单个 LF 的区别；同时校验成功输出恰为一行 64 位
小写十六进制加换行、退出状态为 0、stderr 无失败信息，并保留 `--version`、
参数错误（退出 2）和读取失败（退出 1）的既有行为。

`tests/prove_regression.rs` 对 `roottrace prove` 做同样的端到端保障：固定证明
向量（9 条非二次幂批次的首条、重复内容位置和末条，8 条平衡批次中部，含 NUL/
CR/非 UTF-8 字节的 10 条长短混合批次中的长记录，以及单个 LF 的空路径）逐字节
校验输出的一行 JSON；证明中的 `root` 与 `root` 命令对同一文件的结果一致；
相同内容位于不同位置得到不同证明；末尾 LF 有无两种文件形式给出逐字节相同的
证明；序号越界（含空文件）退出 1 且标准输出为空；负数、非数字、超过 64 位
无符号整数范围、缺少或多余参数退出 2 并输出用法说明；读取失败退出 1 且不输出
残缺证明。

`tests/verify_regression.rs` 对 `roottrace verify` 做端到端保障：直接使用
`tests/reference/rfc6962_vectors.py` 固定的同一批证明常量，另外把每个固定批次
每个位置的真实 `prove` 输出交给 `verify`，覆盖与现有命令的逐字节互操作；成功
时标准输出恰为 `verified\n`、退出 0、标准错误为空。记录文件按**全部字节**
处理——零字节文件核验空记录成功，而追加结束用 LF、空格、CR 或 NUL 都改变
记录并核验失败；含 NUL/CR/非 UTF-8 字节且以非文本字节结尾的长记录原样参与。
证明允许字段重排与任意 JSON 空白；证明自带的 `tree_size`、`root` 与命令行
可信值不一致时核验失败（证明不能自证）；重复内容只按 `leaf_index` 声明的
位置核验；路径缺一个、多一个（含单记录树的非空路径）或调换顺序都失败。空文件、
非对象、必需字段缺失或重复、类型错误、前导零/指数/小数、超出 64 位无符号
范围、非小写或长度不对的十六进制、`tree_size` 为 0 或序号越界、对象后有
多余字节，均以“证明格式无效”退出 1 且标准输出为空。可信树大小（必须为
ASCII 十进制正整数且不超 64 位）或可信根值（恰为 64 位小写十六进制）不合法、
缺少或多余参数退出 2 并输出用法说明；两个输入文件读取失败退出 1。

`tests/verify_escape_regression.rs` 针对证明文件中 JSON 字符串转义的端到端
回归保障（证明经其他 JSON 工具重新保存后，字符可能变成等价的 `\uXXXX`
表示，这种表示变化必须与证明内容损坏明确区分）：必需字段名与
`root`/`audit_path` 中的哈希字符无论直接书写、用合法 `\uXXXX` 转义（转义中
的十六进制字母可大写）还是在一个字符串中混用，解读后的字段与哈希完全相同
时核验结果完全相同（退出 0，标准输出恰为 `verified\n`，标准错误为空）。
重复字段按解读后的名称判断——同一对象中 `root` 与把某个字母写成转义的同名
字段即使值相同也算重复，`tree_size`、`leaf_index`、`audit_path` 同样——一律
按证明格式无效处理（退出 1、标准输出为空、标准错误说明格式问题），不任选
一个值继续核验。非法转义、未写完的 `\uXXXX`、孤立或错误配对的 Unicode 代理
项、字符串内未转义的控制字节与非法 UTF-8 字节同为格式错误。合法转义不放宽
哈希内容限制：解读后出现大写哈希字符、非十六进制字符或长度不符仍是格式
错误；解读后合法但与可信根值不符则保持核验失败。记录文件仍按全部原始字节
参与核验（含 NUL/CR/非 UTF-8 字节的长记录对转义证明核验成功），`prove` 的
原样输出继续直接兼容。

`tests/verify_lf_record_regression.rs` 对**记录本身含有 LF** 的核验做端到端
保障（verify 的记录文件与库收到的记录字节都不按行拆分，LF 可以合法地属于
记录内容，这种记录无法用批次文件表达，因此证明与可信根值全部来自独立脚本
`tests/reference/rfc6962_lf_record_vectors.py`，不由本项目生成再自验）：
一条 100 字节记录以 LF 开头、内部有连续 LF、末尾仍是 LF，同时含 CR、NUL 与
非 UTF-8 字节（叶子输入 101 字节，跨过 SHA-256 的 64 字节分块边界），每个
LF 都是内容——连续 LF 不代表多条空记录，末尾 LF 也不能被当作结束符删掉；
另覆盖恰好只有一个 LF 的记录，它既不是零字节的空记录，也不是批次文件所
表示的一条空记录（与 `6e340b9c...` 的空记录证明互相拒绝）。同一字节规则
在单记录树（空审计路径）与 9 条记录的非二次幂树（目标位置对应的路径）中
都成立：原始记录完全匹配时命令行成功输出仍恰为 `verified\n`、退出 0、
标准错误为空，库返回成功结果并保留正确的序号、可信树大小和根值；记录中
的换行不改变证明声明的树大小与位置，核验也不会转而匹配记录中的某一行。
对同一份合法证明，只删除末尾 LF 或改动内部一个 LF（其余字节不变）都核验
失败：命令行退出 1、标准输出为空、标准错误说明核验失败（而非证明格式
无效），库返回 `VerificationFailed`。

`tests/inspect_regression.rs` 对 `roottrace inspect` 做端到端保障：成功时
标准输出恰为一行、只含 `tree_size`、`leaf_index`、`root` 三个字段的 JSON
加换行，退出 0、标准错误为空，且与真实 `prove` 证明中对应字段逐字节一致、
与 `root` 命令的根值相同；字段重排、任意 JSON 空白以及字段名/哈希字符的
等价 `\uXXXX` 转义显示完全相同的信息。证明格式合法但审计路径数量、顺序或
内容无法证明声明位置（路径过短、多记录树空路径、任意根值）时仍正常显示，
且输出绝不包含 `verified` 等核验成功措辞。完整格式判定与 `verify` 相同：
非对象、截断、对象后多余字节、任一必需字段（含不展示的 `audit_path`）
缺失、`audit_path` 内哈希长度不对/大写/类型错误/数组未结束、重复字段
（含经转义后重名）、类型错误、前导零/小数/指数/超 64 位范围的整数、
`tree_size` 为 0、序号越界，均以证明格式无效退出 1、标准输出为空；
`u64::MAX` 的大小与在范围内的最大序号保持完整 64 位含义。文件不存在或指向
目录退出 1 且标准错误说明读取原因；缺少或多余参数退出 2 并输出用法说明；
同时确认该命令不改变 `verify` 与 `--version` 的既有行为。含非 UTF-8 字节
证明路径的覆盖位于 `tests/non_utf8_paths.rs`。

`tests/long_record_regression.rs` 对**长记录**做同样的端到端保障：记录去掉 LF
分隔符后为 54、55、56、63、64、65 字节（叶子哈希输入 `0x00 || 记录` 相应为
55–57 与 64–66 字节，贴近或跨过 SHA-256 的 56 字节填充边界与 64 字节分块边界）
以及一条 135 字节（>128，叶子输入进入第三个分块）的记录，各自作为单条记录
构成批次时都必须匹配固定根值；每条长记录内部都含 NUL、CR 与非 UTF-8 字节且
以非文本字节结尾，覆盖内容在内部和末尾的字节保真。两条长记录（65 与 135
字节）各有仅改动末尾一个字节的变体，根值必须对应修改后的完整记录——只处理
记录前面部分的实现无法通过。另设一个由长短记录共同组成的 10 条固定批次
（RFC 6962 的 k=8 切分使长记录同时落在左右子树），并同样校验该批次末尾字节
变体，确认长记录在批次中与单条记录时遵守同一标准。所有长记录批次都同时以
"末尾有/无结束用 LF"两种文件形式校验，二者表示同一记录序列、根值相同。

`tests/multi_read_regression.rs` 对**跨多次读取的记录**做端到端保障：`root`
命令以固定 64 KiB 缓冲区分段读取文件，该批次含一条 140000 字节（>128 KiB）
的记录，其字节跨越多次连续读取，读取边界绝不能成为记录边界——长记录按完整
字节恰好参与一次，不被截断、重复计入或拆成多个位置。批次为 10 条记录
（非二次幂，RFC 6962 按 k=8 切分，长记录落在左子树、末尾短记录落在右子树），
同时包含空记录、两处相同内容与结尾短记录；长记录前半段、后半段与末尾各有
可区分内容的标记，内部保留 NUL、CR 与非 UTF-8 字节。一条填充记录把第 2、3
条记录的分隔 LF 恰好放在第一次读取的最后一个字节与第二次读取的第一个字节
（连续 LF 跨过读取边界），每条空记录仍各占一个位置。同一批次末尾有/无结束用
LF 时输出逐字节相同；长记录后半段仅改动一个非 LF 字节后记录数与顺序不变，
根值对应修改后批次的固定值且与原批次不同。预期根值由独立脚本
`tests/reference/rfc6962_multiread_vectors.py` 固定，与
`tests/multi_read_regression.rs` 中的确定性构造逐字节对应同一记录序列。

`tests/multi_read_proof_regression.rs` 在同一跨多次读取批次上对 `prove` 与
`verify` 的联动做端到端保障：分别对位置 4 的 140000 字节长记录与位置 9 的末条
短记录执行 `prove`，输出树大小恰为 10、序号对应所选位置、根值等于完整批次的
独立固定根值、审计路径按从叶子到根排列并准确绑定该位置（10 条沿用 RFC 6962
的不均匀 k=8 树形，不复制末条也不补空记录：长记录路径 4 个哈希，末条路径 2 个，
后者最靠近根的兄弟正是左侧 8 棵叶子的子树哈希）；成功输出仍是一行完整 JSON 加
换行、退出 0、标准错误为空。固定路径与根值来自上述独立脚本中两种结构不同的
路径算法互验、再经独立包含验证器重算回根值，不依赖 prove/root 互比或项目自身
核验成功。批次文件末尾有/无结束用 LF 表示同一十条记录序列，两位置的证明逐字节
相同，且位置 10 不存在（不额外产生空记录）。两份证明连同对应记录的原始字节
（长记录无分隔 LF、二进制字节不被修剪或替换）与独立确认的树大小、根值交给
`verify` 均成功，标准输出恰为 `verified\n`；另外附加结束用 LF 或翻转尾部字节
都以核验失败处理。仅改动长记录后半段一个非 LF 字节（记录数量与位置不变）后，
重新生成的证明绑定变化后的根值：长记录自身的兄弟子树未变，其审计路径逐字节
保持原值；末条短记录内容未变，但其路径中覆盖长记录的左子树哈希随之变化、
叶子侧兄弟哈希不变。原长记录证明配合修改后的记录与原可信根值核验失败——
退出 1、标准输出为空、标准错误归为"核验失败"而非"证明格式无效"；配合修改后
根值同样是核验失败。命令、证明格式与错误分类均保持不变。

`tests/library_verify.rs` 把 roottrace 当作**库**来端到端检验：证明与可信根值由
实际构建出的 CLI（`prove`/`root`）产生，大树情形沿用与
`tests/verify_big_tree_regression.rs` 相同的固定常量，核验本身则全部通过
`roottrace::verify_membership` 在内存中完成。覆盖：CLI 证明在批次每个位置都能
经库核验成功，且返回的类型化结果携带来自证明的序号与调用方的可信树大小、
根值；格式无效、核验失败、可信树大小为零（调用参数无效）三类错误按类型
区分；记录字节保真（空记录、末尾 LF/CR/空格/NUL、非 UTF-8 字节）；字段重排、
空白与等价转义被接受而重复字段仍被拒绝；重复内容只按声明位置核验；2^63、
2^63+1、2^64-1 的树大小与超过 32 位的序号保持完整 64 位含义。

`tests/library_prove.rs` 把 roottrace 当作**库**来检验内存中的证明**生成**
入口 `prove_membership`：对批次文件能表达的序列（1、7、8、9 条，跨过二次幂
边界），在文件末尾 LF 有无两种形式下，逐位置校验生成的单行 JSON 与实际
`prove` 命令输出去掉行末换行后**逐字节一致**、根值与 `root` 命令相同；
`InclusionProof` 的树大小、序号、根值与从叶到根兄弟哈希读取正确，只有一条
记录时路径为空，9 条记录末条路径恰为前 8 条的 MTH（不复制末条、不补空记录）。
记录本身含 LF、CR、NUL 与非 UTF-8 字节（批次文件无法表达）时，单记录树与
9 条非二次幂树的根值和审计路径逐字节等于独立脚本
`tests/reference/rfc6962_lf_record_vectors.py` 固定的常量，生成的 JSON 再用
完整记录字节与独立可信值经 `verify_membership` 与命令行 `verify`/`inspect`
核验成功；内嵌 LF 不被当成分隔符。空切片元素占一个位置而空批次没有任何位置；
重复内容指定靠后出现的位置时不被改成前一次；序号越界、空批次以及 u64::MAX
等高序号都返回按类型识别的 `ProveError::PositionNotFound`，并原样携带请求
序号与实际记录数（高序号不被截断成合法位置），既不 panic 也不返回残缺证明；
JSON 为不含行末换行的单行，并接受 `&[&[u8]]`、`&[Vec<u8>]`、按值的
`Vec<Vec<u8>>` 与固定数组等多种批次传参形式。

`tests/verify_big_tree_regression.rs` 对**大树**（树大小接近 64 位无符号整数上限）
的核验做端到端保障：树大小为 9223372036854775808（2^63，二次幂树）、
9223372036854775809（2^63+1，不均匀树）与 18446744073709551615（2^64-1，不均匀
树）的合法证明都必须核验成功——标准输出恰为 `verified\n`、退出 0、标准错误为空。
这样的批次无法真正物化，因此证明是合成的：固定一条目标记录（含 NUL 与非 UTF-8
字节），路径第 i 个哈希为 i 的 64 位小写十六进制表示，可信根值由
`tests/reference/rfc6962_vectors.py` 用两种结构不同的独立实现（递归下降与自顶向下
记录转向再自叶向根折叠）重算并互验后固定。覆盖每个树大小的首条、末条以及左右
子树交界两侧的位置，包括序号恰为 2^32-1 与 2^32 等超过 32 位范围的情形；可信树
大小与序号必须保持精确整数含义（差 1 即核验失败），不因高位存在而被截断、变负或
被当作较小批次。2^63+1 树的末条记录是右子树唯一叶子，路径恰为一个哈希（不均匀
树形，不复制末尾记录也不补空记录）。同一大树证明的路径少一个、多一个或改动一个
哈希，以及记录字节有任何改动，都核验失败（退出 1、标准输出为空、标准错误说明
核验失败，而非用法错误或异常终止）；记录与路径不变、仅把可信树大小换成另一个
合法数值（含证明自带大小之外的相邻值）同样失败。树大小为 2^64-1 时序号等于树
大小属于证明格式无效（退出 1、标准错误为"证明格式无效"），与合法位置上的核验
失败保持区分。

预期根值不来自被检查的功能：`tests/reference/rfc6962_vectors.py` 是独立的 Python
参考实现（标准库 `hashlib.sha256`，递归定义与栈折叠两种算法互验），运行后可
重新生成各固定记录序列（含上述全部长记录与长短混合批次）对应的根值常量供核对；
跨多次读取批次的固定根值由复用同一对互验算法的
`tests/reference/rfc6962_multiread_vectors.py` 独立生成。
该脚本对包含证明同样提供两种结构不同的算法（RFC 6962 第 2.1.1 节 PATH 的递归
定义，以及自根向叶下降、兄弟子树哈希改用栈折叠计算的写法），二者在每个固定序列
的每个位置上结果一致，再用独立的递归包含验证器把每条证明重新哈希回批次根值；
脚本末尾输出供 `tests/prove_regression.rs` 使用的固定证明常量。
`tests/reference/rfc6962_multiread_vectors.py` 复用同一对路径算法与验证器，
额外输出跨多次读取批次在长记录（位置 4）与末条短记录（位置 9）上、原始批次与
单字节修改批次各自的固定审计路径，供
`tests/multi_read_proof_regression.rs` 使用。
`tests/reference/rfc6962_lf_record_vectors.py` 同样复用该对互验算法与
独立包含验证器，为**本身含有 LF 的记录**（批次文件无法表达）固定单记录树与
9 条非二次幂记录序列各自的根值与审计路径，并独立确认各变异向量（删末尾
LF、改内部一个 LF、记录中的单独一行、空记录对单 LF 位置）都不能重算出
根值，供 `tests/verify_lf_record_regression.rs` 使用。

## 用法

```sh
roottrace root <文件路径>            # 计算批次根值
roottrace prove <文件路径> <记录序号>  # 生成指定记录在整个批次中的成员证明
roottrace inspect <证明文件>          # 只查看证明自身声明的大小、序号与根值
roottrace verify <记录文件> <证明文件> <可信树大小> <可信根值>
                                     # 仅凭一条记录和证明核验其位置，无需完整批次
roottrace --version                  # 打印版本号
```

### `roottrace root <文件路径>`

读取文件中的全部记录，按 RFC 6962 第 2.1 节的 SHA-256 Merkle Tree Hash
计算根值，向标准输出写出一行 64 个小写十六进制字符（行末带换行），退出状态为 0：

```text
b137985ff484fb600db93107c77b0365c80d78f5b429ded0fd97361d077999eb
```

两个文件的根值相同，说明它们的记录序列完全相同；根值不同则内容有差异。

**记录如何划分：** 文件按原始字节读取，以 LF（`\n`，0x0a）分隔记录，分隔符
本身不属于记录。记录中的空格、制表符、CR（`\r`）以及非 UTF-8 字节都属于
记录内容，原样参与计算。文件换行方式会影响根值：使用 CRLF 换行的文件，每条
记录末尾会多出一个 `\r` 字节，与对应 LF 换行的文件根值不同。

**非 UTF-8 文件路径：** 在 Unix 等允许文件名字节不是合法 UTF-8 的系统上，
路径按用户在命令行传入的原始字节原样访问，无需重命名或额外指定编码；相对
路径与绝对路径同样适用。因此路径中出现例如 0xff 字节时，程序不会在读取
文件前异常退出，也不会误读同目录下仅因显示替换字符“�”而看起来同名的另一个
文件。两个文件内容相同而路径字节不同，根值与证明完全相同。路径不存在、
指向目录或读取失败（即使路径本身含非 UTF-8 字节）时仍按下面的规则退出 1。
命令名、记录序号以及 `verify` 的可信树大小与可信根值参数必须是合法 UTF-8
文本；其中出现非 UTF-8 字节按用法错误退出 2。

**空文件与空记录的区别：**

- 空文件（0 字节）表示零条记录，根值是空输入的 SHA-256
  （`e3b0c442...b7852b855`）。
- 只含一个 LF 的文件表示一条空记录，与空文件的根值不同。
- 连续的 LF 会产生空记录，例如 `a\n\n` 是 `a` 和一条空记录。
- 末尾的 LF 只结束最后一条记录，不额外产生空记录，因此 `a\nb` 与 `a\nb\n`
  的根值相同。

重复内容不会被去重或合并：相同字节出现在不同位置仍是不同的记录，记录顺序
也参与计算。

**错误处理：**

- 缺少文件路径、参数多余或命令未知：向标准错误输出用法说明，退出状态为 2。
- 文件不存在、路径是目录或读取失败：向标准错误输出失败原因，退出状态为 1，
  标准输出不会写出任何根值。

### `roottrace prove <文件路径> <记录序号>`

为指定记录生成它在**整个批次**中的 RFC 6962 第 2.1.1 节包含证明（成员证明）。
记录划分规则与 `root` 完全一致（LF 分隔、末尾 LF 不增加记录、空记录占独立
位置、CR/NUL/非 UTF-8 字节原样保留）。

**记录序号（第二个参数）：** 从 0 开始的十进制非负整数，只接受 ASCII 数字，
按文件中的记录顺序定位：`0` 是第一条记录，`1` 是第二条，以此类推。相同内容
出现在多个位置时，证明的是序号指定的那个位置，不会去重，也不会自动改成第一
次出现的位置。序号等于或大于实际记录数时，该位置不存在。例如只含一个 LF 的
文件有一条记录，只能对序号 `0` 生成证明；真正的空文件（0 字节）没有任何可选
记录，对任何序号都报位置不存在。

成功时标准输出恰为一行 JSON 对象（行末带换行），退出状态为 0，标准错误为空：

```sh
$ printf 'a\nb\nc' > batch.txt
$ roottrace prove batch.txt 1
{"tree_size":3,"leaf_index":1,"root":"36642e73c2540ab121e3a6bf9545b0a24982cd830eb13d3cd19de3ce6c021ec1","audit_path":["022a6979e6dab7aa5ae4c3e5e45f7e977112a7e63593820dbec1ec738a24f93c","597fcb31282d34654c200d3418fca5705c648ebf326ec73d8ddef11841f876d8"]}
```

字段含义：

- `tree_size`：JSON 整数，完整批次的记录数。
- `leaf_index`：JSON 整数，被证明记录的序号（即命令行给出的位置）。
- `root`：64 位小写十六进制字符串，与 `roottrace root` 对同一文件输出的
  根值完全相同。
- `audit_path`：字符串数组，每个元素是 64 位小写十六进制哈希，按**从叶子向根**
  的顺序排列（RFC 6962 第 2.1.1 节的成员证明定义）。批次只有一条记录时为空
  数组 `[]`；记录数不是二次幂时按 RFC 的不均匀子树构造证明，既不复制末尾
  记录也不补空记录（例如 9 条记录时最后一条的证明只有一个哈希，即前 8 条
  子树的 MTH）。

证明中**不包含**原始记录：接收方用目标记录的原始字节、`leaf_index`、
`tree_size` 和 `audit_path` 重新哈希并与 `root` 比对，即可核对该记录确实位于
该位置。

**错误处理：**

- 位置不存在（空文件，或序号达到/超过实际记录数）：向标准错误说明该位置
  不存在，退出状态为 1，标准输出为空。
- 序号不是由 ASCII 数字组成的十进制非负整数（负数、非数字、超出 64 位无符号
  整数范围等），或缺少、多余参数：向标准错误输出用法说明，退出状态为 2。
- 文件不存在、路径是目录或读取失败：向标准错误输出失败原因，退出状态为 1，
  标准输出不会写出残缺证明。

### `roottrace inspect <证明文件>`

只查看一份成员证明**自身声明**的内容：批次大小、记录位置和根值。调用者
**不需要**准备目标记录，也**不需要**独立确认的可信树大小和可信根值——这个
操作不做成员核验。它适合在拿到一份证明、还没决定如何核验时快速读出其中的
三个关键信息。

成功时标准输出恰为一行 JSON 对象（行末带换行），**只包含** `tree_size`、
`leaf_index`、`root` 三个字段（整数不打引号，`root` 为 64 个小写十六进制
字符），退出状态为 0，标准错误为空。它直接接受 `prove` 的原样输出：

```sh
$ roottrace prove batch.txt 1 > proof.json
$ roottrace inspect proof.json
{"tree_size":3,"leaf_index":1,"root":"36642e73c2540ab121e3a6bf9545b0a24982cd830eb13d3cd19de3ce6c021ec1"}
```

输出中**没有** `audit_path`（它只被解读、不被展示），也绝不出现
`verified` 或其他表示核验成功的文字。

**显示的值来自证明自身，不能据此信任它们（重要）：**

- 一次成功的 `inspect` 只表示这份证明符合当前的文件格式，**不代表**证明里
  声明的记录已被证明属于该批次。哈希写法合法、但审计路径的哈希数量、顺序或
  内容根本无法把记录结合到声明位置时，`inspect` 仍然照常显示这三个值——
  因为这里既没有目标记录可重算，也没有独立可信值可比对。
- 因此显示出的 `tree_size` 与 `root` **不能**直接拿去当作 `verify` 的可信
  树大小和可信根值：证明可能来自不可信一方，用证明自带的值去核验同一份证明
  等于让证明自我背书。核验成员身份时，可信值仍须来自签名公告、带外账本，或
  对完整批次自行运行 `roottrace root` 等独立渠道，然后使用 `verify`。

```sh
# 下面的做法是错误的：把 inspect 显示的大小和根值当作可信输入，
# 同一份证明会"自我证明"。可信值必须独立获得。
roottrace verify record.bin proof.json 3 36642e73c2540ab121e3a6bf9545b0a24982cd830eb13d3cd19de3ce6c021ec1
```

证明的格式判定与 `verify` **完全相同**，不能只找到三个待显示字段就算成功：
字段重排、合法 JSON 空白（空格、制表符、CR、LF）以及字段名或哈希字符的等价
`\uXXXX` Unicode 转义不改变显示的信息；但证明必须是一个完整的 JSON 对象，
四个必需字段（含不展示的 `audit_path`）齐全且无重复，类型、整数与哈希合法，
`tree_size` 为正，`leaf_index` 在声明范围内。即使损坏位于 `audit_path`
中（例如某个哈希长度不对、数组没有结束），也按证明格式无效拒绝。解读后
重名的字段、`tree_size` 为 0、序号达到或超过声明大小同样拒绝。序号仍从
0 开始；大小和序号保留完整的 64 位无符号整数含义（即使该树无法真正物化，
只要字段在范围内就能显示）。

**错误处理：**

- 证明文件不存在、路径是目录或读取失败：标准输出为空，向标准错误说明读取
  原因，退出状态为 1。路径继续支持系统允许的非 UTF-8 字节，按命令行传入的
  原始字节访问。
- 证明格式无效：标准输出为空，向标准错误说明格式问题，退出状态为 1（与
  `verify` 对同类证明的判定和措辞一致）。
- 缺少或多余参数、命令未知：向标准错误输出用法说明，退出状态为 2。

### `roottrace verify <记录文件> <证明文件> <可信树大小> <可信根值>`

核验 `prove` 生成的包含证明：接收方**不需要完整批次**，只需目标记录本身、
证明，以及独立确认的树大小和根值，就能按 RFC 6962 第 2.1.1 节核对该记录确实
位于证明声明的位置。证明中的 `tree_size`、`root` 必须与命令行给出的可信值
逐字节一致——程序**不会**用证明自带的这两个字段作为信任依据，一份自洽但锚定
到别的树的证明无法通过核验。

**记录文件与批次文件的区别（重要）：**

- `root`/`prove` 的**批次文件**按 LF 分隔多条记录，末尾 LF 只结束最后一条，
  不额外产生空记录；空文件表示零条记录。
- `verify` 的**记录文件**保存**一条**目标记录的原始字节：文件的全部字节就是
  记录内容，**不按 LF 切分**，也**不删除**末尾的换行、空格或 CR。NUL 和非
  UTF-8 字节同样原样参与哈希。
  - 零字节文件表示一条**空记录**，可匹配 `tree_size` 对应树中的相应证明。
  - 若在记录后多写一个结束用 LF，记录内容就变成“原内容 + LF”，必须**核验
    失败**（批次文件里末尾 LF 不算内容；记录文件里每个字节都算）。
  - 从批次中取出记录交给 `verify` 时，应去掉分隔记录的那个 LF，只保留记录
    自身字节。

**可信树大小（第三个参数）：** ASCII 十进制**正整数**（只含数字，无符号、
空白或小数点），值不超过 64 位无符号整数范围；`0` 不接受（不存在包含记录的
零节点树）。

**可信根值（第四个参数）：** 恰好 64 个小写十六进制字符（32 字节），与
`roottrace root` 的输出格式一致。

**可信值从哪里来：** 必须由你**独立确认**，例如来自可信发布渠道（签名公告、
带外账本、对完整批次单独运行 `roottrace root` 等）。证明本身可能来自不可信
一方，所以其中的 `tree_size`/`root` 只用于和你的可信值比对，绝不能替代它们。

成功时标准输出**仅**为 `verified` 加换行，退出状态为 0，标准错误为空：

```sh
$ roottrace verify record.bin proof.json 9 a8a3e76ecf28b850e84cb5465729921212ffd07de3c0e6e170cd233bf723adc3
verified
```

核验流程：

1. 证明的 `tree_size` 必须等于可信树大小；
2. 证明的 `root` 必须等于可信根值；
3. `leaf_index` 必须在树中存在（`0 <= leaf_index < tree_size`）；
4. 从 `SHA-256(0x00 || 记录文件全部字节)` 出发，按证明 `audit_path` 的**原
   顺序**结合（非二次幂批次沿用 RFC 的不均匀树形，既不补记录也不复制末尾
   记录），结合方式由树大小与序号决定；单条记录（`tree_size` 为 1、序号 0）
   的路径必须为空数组 `[]`。
5. 重新算出的根必须等于可信根值。

路径少一个或多一个哈希（含单记录树却带了哈希）、顺序错误，或记录字节、
可信值、位置有任何不匹配，都不能成功。相同内容出现在多个位置时，只按证明
声明的 `leaf_index` 核验，不会搜索其他位置。

证明文件必须是**一个完整的 JSON 对象**，允许字段顺序和空白（空格、制表符、
CR、LF）变化。出现下列任一情况都判定为证明格式无效：不是 JSON 对象；必需字段
缺失或重复；值的类型错误（如整数写成字符串、`root` 不是字符串、
`audit_path` 不是数组）；`tree_size` 或 `leaf_index` 不是规范的 64 位无符号
JSON 整数（负数、小数、指数、前导零、超范围如 `1e400` 等都不行）；`root` 或
路径元素不是 64 位小写十六进制字符串；`tree_size` 为 0；`leaf_index` 越界；
对象之外还有多余字节。

**错误处理：**

- 内容、可信值或路径不匹配（核验失败），或证明格式无效：标准输出为空，向
  标准错误说明原因（分别提示核验失败/证明格式无效），退出状态为 1。
- 文件不存在、路径是目录或读取失败（记录文件或证明文件任一）：向标准错误
  说明原因，退出状态为 1，标准输出为空。路径继续支持系统允许的非 UTF-8 字节，
  按命令行传入的原始字节访问。
- 缺少或多余参数、可信树大小不是 ASCII 十进制正整数或超出 64 位范围、可信
  根值格式不符：向标准错误输出用法说明，退出状态为 2。

## 作为 Rust 库调用

除命令行外，roottrace 同时是一个 Rust 库：其他 Rust 程序可以直接在内存中
核验成员证明，无需准备完整批次或临时文件。在 `Cargo.toml` 中把本包加入
`[dependencies]` 后，成员核验的入口是 `roottrace::verify_membership`；
要在内存中直接**生成**成员证明（无需批次文件或命令行，连记录本身含 LF
的批次也行），入口是 `roottrace::prove_membership`。

下面用一个**含重复记录的小批次**给出可以整段复制的完整示例：记录、证明、
可信值全部作为常量硬编码在程序里，复制后即可编译运行并得到真实的核验结果，
不需要先准备任何输入文件。

### 固定输入：一个 4 条记录的批次

批次文件的全部字节是 `alpha\nbeta\nalpha\ngamma\n`（23 字节，末尾 LF 只
结束最后一条记录）。按 LF 分隔出的完整记录序列为：

| 序号 | 记录字节 | 说明 |
| --- | --- | --- |
| 0 | `alpha`（5 字节） | 与位置 2 的内容完全相同 |
| 1 | `beta`（4 字节） | |
| 2 | `alpha`（5 字节） | **目标位置**：要核验的记录在这里 |
| 3 | `gamma`（5 字节） | |

目标记录是序号 **2** 的 `alpha`。序号从 0 开始；位置 0 虽然与它字节完全
相同，但是树中的另一个位置，对应另一份证明，本次核验不涉及它。

对该文件运行命令行可以直接得到证明与根值，输出逐字节如下：

```sh
$ printf 'alpha\nbeta\nalpha\ngamma\n' > batch.txt
$ roottrace root batch.txt
e63979768f9a2e746fa65d9bc2b3c0c97346fa29188b7346912c9a462b0a4b56
$ roottrace prove batch.txt 2
{"tree_size":4,"leaf_index":2,"root":"e63979768f9a2e746fa65d9bc2b3c0c97346fa29188b7346912c9a462b0a4b56","audit_path":["4c79d0d62f7cf5ca8874155f2d3b875f2625da2bb3abc86bbd6833f25ba90e51","983cb57c04cddd52634edab38a7bef85708a974f114bbd9aa9ec5d4ce6656b4b"]}
```

- **证明**就是上面 `prove` 输出的那一整行 JSON（下面的程序以原始字节常量
  给出，与命令行输出逐字节兼容）。两个审计路径哈希按从叶向根的顺序，依次
  是同层兄弟叶子 `SHA-256(0x00 || "gamma")` 与左半边两棵叶子的父节点
  `MTH(["alpha","beta"])`。
- **可信树大小 4 与可信根值不是从证明里读出来的**，而是用证明之外的完整
  批次数据独立确认的：这里是对同一个批次文件**单独运行 `roottrace root`**
  得到的结果；在真实场景中可换成签名公告或带外账本。下面程序把这 64 个
  十六进制字符写成完整的 32 字节数组，逐字节给满、没有省略。证明里的
  `tree_size`/`root` 只用于和它们比对。

> **字节边界。** 库函数收到的 `record: &[u8]` 是**一条记录的全部内容**：
> 不按 LF 拆分，也不自动删除末尾的换行。从批次文件取出一条记录时，分隔它
> 的那个 LF **不包含**在内——本例的记录就是 5 个字节 `alpha`，不是
> `alpha\n`。因此额外给记录追加一个 LF，记录就变成 6 个字节的另一条记录。
> 另外，空切片 `b""` 表示**一条空记录**（对应只含一个 LF 的批次里的那一条），
> 它与“空树”是两回事：空树没有任何位置，可信树大小为 0 不能用来核验成员。

### 完整程序与实际结果

```rust
use roottrace::{inspect_proof, verify_membership, VerifyError};

fn hex(root: &[u8; 32]) -> String {
    root.iter().map(|b| format!("{b:02x}")).collect()
}

/// 核验一条记录并按“结果类型”报告：成功就读出序号、树大小和根值；失败只
/// 区分错误变体。变体里附带的原因字符串仅供写日志，不要匹配它的固定文字。
fn check(label: &str, record: &[u8], proof: &[u8], trusted_size: u64, trusted_root: &[u8; 32]) {
    print!("{label}: ");
    match verify_membership(record, proof, trusted_size, trusted_root) {
        Ok(membership) => println!(
            "核验成功：位置 {}，树大小 {}，根值 {}",
            membership.leaf_index(),
            membership.tree_size(),
            hex(membership.root()),
        ),
        Err(VerifyError::MalformedProof(_)) => println!("MalformedProof（证明不符合完整格式）"),
        Err(VerifyError::VerificationFailed(_)) => println!("VerificationFailed（格式合法但不匹配）"),
        Err(VerifyError::InvalidTrustedSize) => println!("InvalidTrustedSize（可信树大小为零）"),
    }
}

fn main() {
    // 批次文件 alpha\nbeta\nalpha\ngamma\n 的完整记录序列（LF 分隔记录，
    // 末尾 LF 只结束最后一条，不属于任何记录）：
    //   位置 0 = "alpha"
    //   位置 1 = "beta"
    //   位置 2 = "alpha"   <- 目标记录；与位置 0 的字节完全相同
    //   位置 3 = "gamma"
    let record: &[u8] = b"alpha";

    // `roottrace prove <批次文件> 2` 的原样输出：完整 JSON，没有任何省略。
    let proof: &[u8] = br#"{"tree_size":4,"leaf_index":2,"root":"e63979768f9a2e746fa65d9bc2b3c0c97346fa29188b7346912c9a462b0a4b56","audit_path":["4c79d0d62f7cf5ca8874155f2d3b875f2625da2bb3abc86bbd6833f25ba90e51","983cb57c04cddd52634edab38a7bef85708a974f114bbd9aa9ec5d4ce6656b4b"]}"#;

    // 可信值独立于证明获得：对上面的“完整批次”运行 `roottrace root`
    // （生产中也可以来自签名公告或带外账本）。批次有 4 条记录，根值是
    // 下面这 32 个字节，逐字节对应上面的证明，但不是从证明里照抄的。
    let trusted_tree_size: u64 = 4;
    let trusted_root: [u8; 32] = [
        0xe6, 0x39, 0x79, 0x76, 0x8f, 0x9a, 0x2e, 0x74,
        0x6f, 0xa6, 0x5d, 0x9b, 0xc2, 0xb3, 0xc0, 0xc9,
        0x73, 0x46, 0xfa, 0x29, 0x18, 0x8b, 0x73, 0x46,
        0x91, 0x2c, 0x9a, 0x46, 0x2b, 0x0a, 0x4b, 0x56,
    ];

    // 1) 原记录 + 原证明 + 独立可信值：核验成功。
    check("原记录", record, proof, trusted_tree_size, &trusted_root);

    // 2) 记录末尾追加一个 LF，证明和可信值都不变：这是另一条记录，必失败。
    let mut with_lf = record.to_vec();
    with_lf.push(b'\n');
    check("加 LF", &with_lf, proof, trusted_tree_size, &trusted_root);

    // 3) 证明被截断（数组和对象都没结束）：不符合完整格式。
    check("截断证明", record, &proof[..proof.len() - 3], trusted_tree_size, &trusted_root);

    // 4) 可信树大小传 0：调用参数无效；这与“空记录”无关。
    check("大小为零", record, proof, 0, &trusted_root);

    // 5) inspect_proof 只读出证明自己的声明，完全不核验成员身份。
    let claims = inspect_proof(proof).expect("这份证明格式合法");
    println!(
        "inspect：证明自称 位置 {}、树大小 {}、根值 {}（未核验，不能当可信输入）",
        claims.leaf_index(),
        claims.tree_size(),
        hex(claims.root()),
    );

    // 6) 空切片表示一条空记录。下面是“只含一个 LF 的批次”（一条空记录、
    //    树大小 1、审计路径为空）的真实证明与独立根值。
    let empty_proof: &[u8] = br#"{"tree_size":1,"leaf_index":0,"root":"6e340b9cffb37a989ca544e6bb780a2c78901d3fb33738768511a30617afa01d","audit_path":[]}"#;
    let empty_root: [u8; 32] = [
        0x6e, 0x34, 0x0b, 0x9c, 0xff, 0xb3, 0x7a, 0x98,
        0x9c, 0xa5, 0x44, 0xe6, 0xbb, 0x78, 0x0a, 0x2c,
        0x78, 0x90, 0x1d, 0x3f, 0xb3, 0x37, 0x38, 0x76,
        0x85, 0x11, 0xa3, 0x06, 0x17, 0xaf, 0xa0, 0x1d,
    ];
    let m = verify_membership(b"", empty_proof, 1, &empty_root).expect("空记录应核验成功");
    println!("空记录：位置 {}，树大小 {}", m.leaf_index(), m.tree_size());
}
```

实际运行结果如下，每一行对应程序中的一次调用：

```text
原记录: 核验成功：位置 2，树大小 4，根值 e63979768f9a2e746fa65d9bc2b3c0c97346fa29188b7346912c9a462b0a4b56
加 LF: VerificationFailed（格式合法但不匹配）
截断证明: MalformedProof（证明不符合完整格式）
大小为零: InvalidTrustedSize（可信树大小为零）
inspect：证明自称 位置 2、树大小 4、根值 e63979768f9a2e746fa65d9bc2b3c0c97346fa29188b7346912c9a462b0a4b56（未核验，不能当可信输入）
空记录：位置 0，树大小 1
```

成功时从类型化结果 `Membership` 读取三个值：

- `leaf_index()` 返回 `2`——证明声明的、从 0 开始的记录序号。它只锚定
  位置 2；位置 0 那条同内容的 `alpha` **并不因此**被视为已核验（对它要
  另行用 `prove batch.txt 0` 生成的、`leaf_index` 为 0 的另一份证明）。
- `tree_size()` 返回 `4`——就是你传入的可信树大小（已与证明自带字段核对
  一致），不是从证明里另读出来的值。
- `root()` 返回那 32 个字节（`&[u8; 32]`）——就是你的可信根值，写成十六
  进制为 `e63979768f9a2e746fa65d9bc2b3c0c97346fa29188b7346912c9a462b0a4b56`，
  与 `roottrace root` 对该批次的输出逐字节相同。

“加 LF”一行演示字节边界的后果：只给目标记录末尾多追加一个 LF（记录变成
`alpha\n`），证明与可信值原封不动，结论就只能是核验失败，不会再出现成功
结果。

### 三类错误按类型区分，不要匹配原因字符串

处理 `Err(VerifyError)` 时要按**变体（类型）**分支决定怎么办；变体附带的
原因字符串只用于写日志，其文字可能调整，不要依赖它的固定措辞：

- `VerifyError::MalformedProof(reason)`：证明不符合**完整格式**——不是一个
  完整 JSON 对象、必需字段缺失或重复、值的类型错误、整数或哈希不合法、
  证明内 `tree_size` 为 0、序号越界、对象后有多余字节等。上例把证明末尾
  截掉 3 个字节即属此类。
- `VerifyError::VerificationFailed(reason)`：证明**格式合法**，但记录内容、
  可信树大小、可信根值或审计路径对不上。记录多一个 LF、可信值换成别的
  批次、证明自带大小/根值与可信值不一致、路径缺一个/多一个/顺序错，都归
  这一类。
- `VerifyError::InvalidTrustedSize`：调用参数无效——可信树大小为 0。该判断
  在解读证明**之前**完成，所以即便拿到的是一份内部 `tree_size` 为 0 的
  “证明”，报的也是这个类型而非格式错误。不存在包含记录的零节点树，它不是
  “空树中的成员证明”。

### `inspect_proof` 只读声明，其结果不能当可信输入

只想读证明自身的声明而不核验时，用
`roottrace::inspect_proof(&[u8]) -> Result<ProofClaims, InspectError>`：它用
与 `verify_membership` 完全相同的完整格式判定解读证明，成功则返回证明自称
的 `tree_size()`、`leaf_index()` 与 `root()`。但这一步**没有目标记录、没有
独立可信值，因此不做成员核验**——审计路径的哈希能否把记录结合到声明位置
完全不检查；只要格式合法，哪怕路径是随便填的，这些字段也会被原样读出。

所以一次成功的 `inspect_proof` 只表示“读出了证明自己的声明”。上例第 5 步
打印出的大小 4 与根值恰好和真值相同，仅仅因为这份证明确实是我们自己对真实
批次生成的；**绝不能**把 `claims.tree_size()`/`claims.root()` 直接回传给
`verify_membership` 去核验同一份证明——证明可能来自不可信一方，那样做等于
让证明自我背书。可信值仍须来自 `roottrace root`、签名公告或带外账本等
独立渠道。证明格式无效时返回 `InspectError::MalformedProof`；命令行的
`inspect` 子命令就建立在这个函数之上。

### `prove_membership` 直接在内存中生成证明

`verify_membership` 需要一份已经存在的证明；要在**没有批次文件、也不调用
命令行**的情况下直接生成证明，用

```rust
roottrace::prove_membership<I, R>(records: I, leaf_index: u64)
    -> Result<InclusionProof, ProveError>
```

其中 `records` 是内存中一个已经划分好的有序记录批次，`leaf_index` 是从 0
开始的序号。它接受任何可按引用迭代出字节串的集合：`&[&[u8]]`、`&[Vec<u8>]`、
按值传入的 `Vec<Vec<u8>>`、固定数组等都可以。成功返回的 `InclusionProof`
提供这些读取方法：

- `tree_size() -> u64`：整个批次的记录数；
- `leaf_index() -> u64`：被证明记录的序号（即你传入的位置）；
- `root() -> &[u8; 32]`：整个批次的 32 字节根值，与 `roottrace root` 对同一
  记录序列的结果完全相同；
- `audit_path() -> &[[u8; 32]]`：从叶子到根排列的兄弟哈希，只有一条记录时
  为空；
- `to_json() -> String`：与 `roottrace prove` **逐字节一致**的单行 JSON
  （紧凑形式、固定字段顺序、小写十六进制），**不含**行末换行，也不包含
  原始记录。需要写入文件或交给命令行时由你自行补一个换行。

**记录边界（重要）：** 与命令行的批次文件不同，传给 `prove_membership` 的
批次**不会再按 LF 拆分**——集合中的**每个元素就是一条完整记录**。记录开头、
内部或末尾的 LF，以及 CR、空格、NUL 和非 UTF-8 字节，全部属于该记录内容，
不修剪也不替换。因此元素 `b"a\nb"` 是**一条**内容含 LF 的记录，而不是
`a`、`b` 两条。空切片 `b""` 元素占**一个**位置（一条空记录，根值为
`6e340b9c...` 的 `SHA-256(0x00)`），它与零个元素的**空批次**是两回事；
重复内容按实际位置保留，指定靠后那次出现的位置不会被改成前一次；记录顺序
参与根值计算。这让“记录本身含 LF”的批次也能直接生成证明——这种序列无法
用 LF 分隔的批次文件表达。

下面这段在前面 4 条记录批次（`alpha/beta/alpha/gamma`）上直接生成位置 2
的证明，输出的 JSON 与文档前面 `roottrace prove batch.txt 2` 的那一行
逐字节相同：

```rust
use roottrace::{prove_membership, ProveError};

let records: [&[u8]; 4] = [b"alpha", b"beta", b"alpha", b"gamma"];
let proof = prove_membership(&records, 2).expect("位置 2 存在");
assert_eq!(proof.tree_size(), 4);
assert_eq!(proof.leaf_index(), 2);
assert_eq!(
    proof.to_json(),
    "{\"tree_size\":4,\"leaf_index\":2,\"root\":\"e63979768f9a2e746fa65d9bc2b3c0c97346fa29188b7346912c9a462b0a4b56\",\"audit_path\":[\"4c79d0d62f7cf5ca8874155f2d3b875f2625da2bb3abc86bbd6833f25ba90e51\",\"983cb57c04cddd52634edab38a7bef85708a974f114bbd9aa9ec5d4ce6656b4b\"]}"
);
```

含 LF 的记录直接作为一个元素即可；只有一条记录时审计路径为空：

```rust
// 一条以 LF 开头、内部有 LF、末尾也是 LF 的完整记录（批次文件无法表达）。
let lf_batch: [&[u8]; 1] = [b"\nline-1\nline-2\n"];
let single = roottrace::prove_membership(&lf_batch, 0).unwrap();
assert_eq!(single.tree_size(), 1);
assert!(single.audit_path().is_empty());

// 生成结果可直接交给核验；可信值须独立确认，不能直接照抄证明里的 root。
let record = lf_batch[0];
let size = single.tree_size();
let trusted_root = *single.root(); // 示例中就地取得；真实场景应来自独立渠道
roottrace::verify_membership(record, single.to_json().as_bytes(), size, &trusted_root)
    .expect("用完整记录字节和可信值核验成功");
```

**错误结果：** 序号达到或超过记录数时返回
`ProveError::PositionNotFound { requested_index, record_count }`——一个可按
**类型**识别的错误，携带你请求的序号（完整 64 位，不截断）和批次实际记录
数。空批次对任何序号都返回这同一类错误，而不是异常终止或给出一份“空树
成员证明”：

```rust
let empty: [&[u8]; 0] = [];
match roottrace::prove_membership(&empty, 0) {
    Err(ProveError::PositionNotFound { requested_index, record_count }) => {
        assert_eq!(requested_index, 0);
        assert_eq!(record_count, 0); // 空批次
    }
    Ok(_) => panic!("空批次没有任何可证明的位置"),
}
```

非二次幂的奇数条记录继续沿用 RFC 6962 的不均匀树形，既不复制末条也不补空
记录（例如 9 条记录时末条的证明只有一个哈希，即前 8 条的 MTH）。生成的
JSON 可直接交给 `inspect_proof`、`verify_membership` 以及命令行的
`inspect`/`verify`。需要提醒：`prove_membership` 返回的 `root()` 只是对你
**自己提交的批次**的计算结果，并不代表它已经获得外部信任；把证明发给别人
时，对方仍应通过独立渠道确认树大小和根值。

### 其他约定

库本身不向标准输出或标准错误打印任何内容；成功与失败如何展示完全由调用方
决定，失败时只返回上述错误，不会返回任何表示已核验成功的结果。命令行的
`verify` 子命令与库函数走完全相同的核验代码，两边对同一输入的结论一致。
树大小和序号始终保持完整的 64 位无符号整数含义，即使超过平台的指针宽度也
不会被截断。
